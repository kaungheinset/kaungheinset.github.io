01 / CONTEXT

Project overview

I built a small, segmented environment to investigate how suspicious Windows and network activity becomes security telemetry, alerts, and defensive action. The lab models a Windows domain, client workstation, security monitoring server, firewall, and separate honeypot network.

The focus is not just installing tools: it is validating whether an activity produces usable evidence, understanding the event trail, and adjusting detection logic.

02 / WORKFLOW

My approach

  • Network design: configured a pfSense firewall with separate internal LAN and DMZ segments.
  • Windows domain: set up Windows Server 2022 with Active Directory and a domain-joined Windows 10 workstation.
  • Telemetry: enrolled Windows hosts into Wazuh and collected Windows Security and Sysmon events.
  • Detection testing: ran controlled authentication and process-behavior tests, then reviewed alerts and correlated logs.
  • Defense in depth: used CrowdSec to test automated source blocking and hosted a T-Pot honeypot in the DMZ.

03 / OBSERVATIONS

Selected findings

01

Custom process-chain detection

Created and validated a custom Wazuh rule for PowerShell spawning cmd.exe (rule 100200; MITRE T1059.003 mapping).

02

Authentication evidence

Investigated unsuccessful Windows sign-ins, including Security Event ID 4625, as part of a controlled RDP brute-force scenario.

03

Automated blocking

Observed CrowdSec ban an attacking Kali lab address during simulated login attacks, confirming a response control in the test setup.

04 / NEXT ITERATION

What comes next

Continue adding documented detection scenarios and testing telemetry quality. Planned work includes broader Atomic Red Team simulation and more structured incident write-ups. These are planned activities, not completed results.
